Section 02

The Data Layer

Instead of hardcoding text into components, we store all content in JSON files and let a pipeline deliver it. This makes future backend integration seamless.

The four-step pipeline

JSON data
→
TypeScript types
→
API function
→
Component

Let's walk through each step:

Step 1: JSON Data — The content lives here

All page content is stored in JSON files inside the data/ folder. For example, data/home.json contains every homepage section:

{
  "hero": {
    "media": { "type": "image", "src": "/images/hero/hero-desktop.jpg", ... },
    "headline": "Wrap Yourself in Comfort",
    "ctas": [{ "label": "Shop Now", "href": "/collections/all", "variant": "primary" }]
  },
  "categoryTiles": {
    "heading": "Shop by Category",
    "tiles": [
      { "image": "/images/categories/category-1.jpg", "label": "Hoodies", ... }
    ]
  },
  "valueProps": { ... },
  "splitBanner": { ... }
}

Similarly, data/navigation.json holds the header navigation, announcement bar messages, and mega menu links.

Why JSON? Right now we don't have a backend. JSON files act as a stand-in. When the Laravel API is ready, we'll swap import rawHome from '@/data/home.json' with fetch('https://api.thehoodielb.com/home') — the component code stays the same because it only cares about the shape of the data, not where it comes from.

Step 2: TypeScript Types — The shape contract

Each JSON file has a matching type definition in the types/ folder. These types describe exactly what shape the data must have:

// types/home.ts

export interface HeroSection {
  media: HeroMedia;
  eyebrow?: string;          // the "?" means optional
  headline: string;           // required
  subcopy?: string;
  ctas: CTA[];                // an array of call-to-action buttons
  align?: 'left' | 'center';  // only these two values allowed
  overlayOpacity?: number;
}

export interface CategoryTile {
  image: string;
  alt: string;
  label: string;
  href: string;
}

Why types? TypeScript will catch mistakes at build time. If someone adds a tile but forgets the alt property, the build fails with a clear error instead of crashing in the user's browser. Types are the contract between data and UI.

Step 3: API Functions — The middleman

API functions in lib/api/ import the JSON, cast it to the correct type, and export an async function:

// lib/api/home.ts

import rawHome from '@/data/home.json';
import type { HomePageData } from '@/types';

const home = rawHome as HomePageData;

export async function getHomePage(): Promise<HomePageData> {
  return home;
}

Notice it's async even though it just returns a local object. That's deliberate — when we switch to fetching from a real API, the function signature stays the same. Nothing that calls getHomePage() needs to change.

Similarly, lib/api/navigation.ts exports getNavigation() and getAnnouncements().

Step 4: Server Component — Fetching and rendering

The page component calls the API function and passes the data to each section component:

// app/page.tsx (the homepage)

import { Hero } from '@/components/sections/Hero';
import { CategoryTiles } from '@/components/sections/CategoryTiles';
import { ValueProps } from '@/components/sections/ValueProps';
import { SplitBanner } from '@/components/sections/SplitBanner';
import { getHomePage } from '@/lib/api/home';

export default async function Home() {
  const home = await getHomePage();

  return (
    <>
      <Hero data={home.hero} />
      <CategoryTiles data={home.categoryTiles} />
      <ValueProps data={home.valueProps} />
      <SplitBanner data={home.splitBanner} />
    </>
  );
}

This is a Server Component (no 'use client' at the top). It runs on the server, fetches data, and sends finished HTML to the browser — fast, SEO-friendly, zero JavaScript shipped for these sections.

The beauty of this pattern: Each section component is completely independent. <Hero> doesn't know or care about <CategoryTiles>. They each receive their data through a data prop and render it. This makes components reusable, testable, and easy to rearrange.

Announcement Bar

What it does

Key concepts in this component

'use client' — Why this component needs it

The announcement bar has interactive features: auto-rotating messages, click handlers for prev/next, and a dismiss button. These all require JavaScript running in the browser, so the component starts with 'use client'.

Remember: in Next.js App Router, components are Server Components by default (no JS shipped). The moment you need useState, useEffect, or click handlers, you must opt in with 'use client'.

State management with useState

The component manages three pieces of state:

const [activeIndex, setActiveIndex] = useState(0);     // which message is showing
const [isVisible, setIsVisible] = useState(true);       // has user dismissed the bar?
const [isPaused, setIsPaused] = useState(false);        // paused on hover?

Each useState creates a value and a setter function. When the setter is called, React re-renders the component with the new value. That's how the message changes on screen without you touching the DOM manually.

useEffect & auto-rotation timer

useEffect runs side effects — things that happen outside the normal render cycle. Here it sets up a timer:

useEffect(() => {
  if (count <= 1 || isPaused || !isVisible) return;

  timerRef.current = setTimeout(() => {
    transitionTo((activeIndex + 1) % count);
  }, 5000);   // 5 seconds

  return () => {
    if (timerRef.current) clearTimeout(timerRef.current);
  };
}, [activeIndex, count, isPaused, isVisible]);

Every time activeIndex changes (a new message shows), the effect re-runs and sets a new 5-second timer. The return function is the cleanup — it clears the old timer to prevent overlapping timers. This pattern (set a timer, clean up the old one) is the standard React way to handle intervals.

Fade transition with CSS + state

Instead of instantly swapping messages, we fade between them. The transitionTo function does this in two steps:

const transitionTo = useCallback((nextIndex: number) => {
  setIsFading(true);       // 1. start fading out (opacity goes to 0)
  setTimeout(() => {
    setActiveIndex(nextIndex);  // 2. swap the content while invisible
    setIsFading(false);         // 3. fade back in (opacity goes to 1)
  }, 300);                      // wait 300ms for the fade-out to finish
}, []);

The CSS handles the actual animation: .announcement-bar__message--fading { opacity: 0; } with a transition: opacity 0.3s. The JS just toggles the class.

useCallback — Why wrap functions?

You'll see useCallback wrapping most handler functions in our components:

const goToNext = useCallback(() => {
  transitionTo((activeIndex + 1) % count);
}, [activeIndex, count, transitionTo]);

What it does: useCallback memorizes a function so React doesn't recreate it on every render. Without it, the function is a new object each render, which can cause child components to re-render unnecessarily.

The array at the end ([activeIndex, count, transitionTo]) lists the dependencies — the function only gets recreated when one of those values changes.

Accessibility note: The message area uses aria-live="polite" and aria-atomic="true". This tells screen readers to announce the new message when it changes, but to wait until the user is idle (polite) rather than interrupting (assertive).
Section 05

Sticky Header & Desktop Navigation

The main site header — logo, navigation links, icons for search/account/cart. It sticks to the top and compacts on scroll.

How the header is structured

Left: Nav Links
Center: Logo
Right: Icons

On desktop, the left zone shows navigation links. On mobile, it shows a hamburger menu button. The logo is always centered, and the right zone has search, account, and cart icons.

Key concepts

Sticky positioning & compact mode

The header uses position: sticky; top: 0; in CSS, so it stays visible as you scroll. But we also make it smaller (compact) once you scroll past a threshold:

// Header.tsx uses IntersectionObserver, not scroll events

const observer = new IntersectionObserver(
  ([entry]) => {
    setIsCompact(!entry.isIntersecting);
  },
  { threshold: 0, rootMargin: '-80px 0px 0px 0px' },
);

observer.observe(sentinel);

IntersectionObserver is more performant than listening to scroll events. We place an invisible "sentinel" <div> at the top of the page. When it scrolls out of view (past 80px), the observer fires and sets isCompact = true.

In compact mode, the header height shrinks from 88px to 64px, giving more screen space to content.

Transparent variant for the hero

The header supports a variant prop:

<Header navItems={navigation.main} variant="transparent" />

When variant="transparent", the header starts with a transparent background so the hero image shows through. Once you scroll (compact mode activates), it becomes solid. This is handled by CSS classes:

.header--transparent {
  background: transparent;
  color: white;
}

The homepage uses :has() in CSS to detect whether the hero section is present:

/* Auto-detect: if page starts with .hero, make header transparent */
main:has(> .hero:first-child) ~ .header {
  /* transparency styles */
}

The :has() selector is a relatively new CSS feature that lets you style a parent based on its children. Here it says: "if the <main> tag's first child is a .hero, then style the adjacent .header differently."

Hover intent — delayed menu opening

If a mega menu opened instantly when your mouse touched a nav link, it would be annoying — you'd trigger menus constantly while moving your mouse across the header. The solution is hover intent:

const HOVER_INTENT_MS = 150;  // delay before opening
const HOVER_CLOSE_MS = 150;   // delay before closing

// First hover — open with delay
hoverIntentRef.current = setTimeout(() => {
  setOpenMenuIndex(index);
}, HOVER_INTENT_MS);

// Already open — switch instantly (no delay)
if (openMenuIndexRef.current !== null) {
  setOpenMenuIndex(index);  // instant switch
}

The first menu takes 150ms to open (proving you meant to hover, not just pass over). But once one menu is open, switching to another is instant — no delay, because you're clearly browsing menus.

Header ↔ MobileNav communication

The hamburger button is in the Header, but the drawer is a separate MobileNav component. They communicate via a custom DOM event:

// Header.tsx — sends the event
const handleMobileMenuOpen = useCallback(() => {
  window.dispatchEvent(new CustomEvent('toggle-mobile-nav'));
}, []);

// MobileNav.tsx — listens for the event
useEffect(() => {
  const handler = () => setIsOpen(prev => !prev);
  window.addEventListener('toggle-mobile-nav', handler);
  return () => window.removeEventListener('toggle-mobile-nav', handler);
}, []);

Why not just lift state up? Both components are 'use client' but they sit at different points in the component tree (they're siblings in layout.tsx). Lifting state to layout.tsx would force it to become a client component, losing the server-rendering benefit. The custom event keeps both components self-contained.

The skip-to-content link: The header includes <a href="#main-content" className="skip-to-content">Skip to content</a>. This is an accessibility feature — keyboard users can press Tab once and skip past all the navigation links straight to the main content. It's visually hidden until focused.

Promo Tile

Each mega menu has two zones: a columns area with grouped navigation links, and a promos area with image-driven promotional tiles. The data comes from navigation.json:

"megaMenu": {
  "columns": [
    {
      "title": "By Style",
      "links": [
        { "label": "Classic Hoodies", "href": "/collections/classic" },
        { "label": "Zip-Up Hoodies", "href": "/collections/zip-up" }
      ]
    }
  ],
  "promos": [
    { "image": "/images/promos/new-arrivals.jpg", "title": "New Arrivals", "href": "...", "badge": "New" }
  ]
}

Key concepts

Keyboard focus management

When a menu opens via keyboard (Enter/Space on a trigger), focus must move into the panel so keyboard users can navigate the links. When they press Escape, focus returns to the trigger:

// Focus first link when opened via keyboard
useEffect(() => {
  if (isOpen && focusOnOpen && panelRef.current) {
    requestAnimationFrame(() => {
      const firstLink = panelRef.current?.querySelector('a');
      firstLink?.focus();
    });
  }
}, [isOpen, focusOnOpen]);

// In Header.tsx — Escape returns focus to trigger
if (e.key === 'Escape') {
  setOpenMenuIndex(null);
  triggerRefs.current[idx]?.focus();  // focus the button that opened it
}

requestAnimationFrame waits one render cycle so the panel is visible before moving focus. Without it, the browser might try to focus an element that hasn't appeared yet.

aria attributes for accessibility

The trigger button and panel are linked with ARIA attributes so screen readers understand the relationship:

// Trigger button
<button
  aria-expanded={openMenuIndex === index}    // "Is this menu open?"
  aria-controls={`mega-menu-${index}`}       // "It controls this panel"
>
  {item.label}
</button>

// Panel
<div
  id={`mega-menu-${index}`}                  // matches aria-controls
  role="region"                               // "This is a content region"
  aria-label={`${viewAllLabel} menu`}         // "Called 'Hoodies menu'"
>

aria-expanded tells screen readers whether the associated panel is open. aria-controls says which element this button controls. The id on the panel matches. These attributes cost nothing visually but make the site usable for anyone using a screen reader.

The backdrop overlay

When a mega menu is open, a semi-transparent dark overlay covers the page behind it. This creates visual focus on the menu and lets users click the backdrop to close:

<div
  className={`mega-menu-backdrop ${
    openMenuIndex !== null ? 'mega-menu-backdrop--visible' : ''
  }`}
  onClick={() => setOpenMenuIndex(null)}
  aria-hidden="true"
/>

The backdrop is always in the DOM — it transitions from opacity: 0; pointer-events: none to opacity: 1; pointer-events: auto when the --visible class is added. This gives a smooth fade transition.

Mobile Navigation Drawer

A slide-in drawer from the left side of the screen, with accordion sub-menus, promo tiles, and social links.

Structure

The mobile nav is divided into four zones stacked vertically:

ZoneContents
Top barClose button + search link
MenuNav items with accordion sub-menus
PromosHorizontal scroll of promotional tiles
FooterAccount link, currency, social icons

Key concepts

Focus trap — keeping keyboard users inside

When the drawer opens, a keyboard user pressing Tab should cycle through elements inside the drawer, not escape to the hidden page behind it. This is called a focus trap:

const handleKeyDown = (e: KeyboardEvent) => {
  if (e.key === 'Escape') { close(); return; }
  if (e.key !== 'Tab') return;

  const focusable = drawer.querySelectorAll(
    'a[href], button:not([disabled]), input, [tabindex]:not([tabindex="-1"])'
  );
  const first = focusable[0];
  const last = focusable[focusable.length - 1];

  // Tab on last element → wrap to first
  if (!e.shiftKey && document.activeElement === last) {
    e.preventDefault();
    first.focus();
  }
  // Shift+Tab on first element → wrap to last
  if (e.shiftKey && document.activeElement === first) {
    e.preventDefault();
    last.focus();
  }
};

We find all focusable elements, then intercept Tab presses at the boundaries. When you Tab past the last element, focus jumps back to the first. Shift+Tab on the first jumps to the last. This creates an invisible loop.

Body scroll lock

When the drawer is open, the page behind it should not scroll:

useEffect(() => {
  if (isOpen) {
    document.body.style.overflow = 'hidden';
  } else {
    document.body.style.overflow = '';
  }
  return () => { document.body.style.overflow = ''; };
}, [isOpen]);

Setting overflow: hidden on the body prevents scrolling. The cleanup function (return) resets it when the component unmounts, preventing a bug where the page stays locked if the component is removed while the drawer is open.

Accordion sub-menus

Nav items with mega menu data expand/collapse as accordions on mobile. Only one can be open at a time:

const [expandedIndex, setExpandedIndex] = useState<number | null>(null);

const toggleAccordion = useCallback((index: number) => {
  setExpandedIndex(prev => prev === index ? null : index);
}, []);

If you click the currently expanded item, it collapses (null). If you click a different item, it opens that one — which automatically closes the previous one because there's only one expandedIndex state.

The expand/collapse animation is handled in CSS with max-height and overflow: hidden transitions.

Close on route change

When a user taps a link inside the drawer, the page navigates. The drawer should close automatically:

const pathname = usePathname();

useEffect(() => {
  if (isOpen) close();
}, [pathname]);

usePathname() is a Next.js hook that returns the current URL path. When it changes (navigation happened), the effect runs and closes the drawer. This saves the user from having to manually close it after clicking a link.

Focus restoration: When the drawer opens, we store document.activeElement (the hamburger button). When it closes, we call prevFocusRef.current?.focus() to return focus to that button. This is critical for keyboard users — they need to know where they are after the drawer closes.

Hero Section

The full-width banner at the top of the homepage — a background image or video, headline text, and call-to-action buttons.

How it works

The Hero is a Server Component (no 'use client') because it has no interactivity — no click handlers, no state. It just receives data and renders HTML. This means zero JavaScript is shipped to the browser for this component.

Background Image/Video
+
Gradient Overlay
+
Text + CTAs

Key concepts

Art direction with next/image

Different screens need different image crops. A wide landscape shot looks great on desktop but loses detail on a phone. Art direction means serving a different crop for each screen:

// Desktop image
<Image
  src={media.src}
  alt={media.alt}
  fill
  sizes="100vw"
  preload
  className="hero__img hero__img--desktop"
/>

// Mobile image (if separate crop provided)
{media.mobileSrc && (
  <Image
    src={media.mobileSrc}
    fill
    sizes="100vw"
    preload
    className="hero__img hero__img--mobile"
  />
)}

CSS then shows/hides the right version:

.hero__img--mobile  { display: block; }
.hero__img--desktop { display: none; }

@media (min-width: 768px) {
  .hero__img--mobile  { display: none; }
  .hero__img--desktop { display: block; }
}
next/image fill mode & the preload prop

The fill prop makes the image fill its parent container (the parent must have position: relative). This is how the hero background works — the image stretches to cover the full section.

The sizes prop tells the browser how wide the image will be at different viewports. "100vw" means "full viewport width" — the browser can then pick the right resolution from the srcset Next.js generates.

Important Next.js 16 change: The old priority prop is deprecated. Use preload instead. This tells the browser to start downloading the image immediately (before the page finishes parsing), which is critical for the hero since it's the first thing users see.

The gradient overlay

A semi-transparent gradient sits between the background image and the text, ensuring text is always readable regardless of the image:

<div
  className="hero__overlay"
  style={{
    '--hero-overlay-opacity': overlayOpacity,
  } as React.CSSProperties}
/>

The overlay opacity is configurable from the JSON data (default 0.45). The CSS uses it:

.hero__overlay {
  background: linear-gradient(
    to right,
    rgba(0,0,0, var(--hero-overlay-opacity)) 0%,
    rgba(0,0,0, calc(var(--hero-overlay-opacity) * 0.3)) 100%
  );
}

This technique — a CSS custom property set via inline style — is how you pass dynamic values from React to CSS without generating unique class names.

Negative margin trick

The hero needs to sit behind the sticky header, so the background image extends under it. This is achieved with negative margin:

.hero {
  margin-top: calc(-1 * var(--header-h));
  padding-top: var(--header-h);
}

This pulls the hero up by the header's height so they overlap. The padding pushes the content (text + buttons) back down so it doesn't hide under the header. The result: a full-bleed hero that flows under a transparent header.

Video support: The hero supports video backgrounds too. It renders a <video autoPlay muted loop playsInline> with a poster image fallback for reduced-motion preferences. The component uses sub-components (HeroImage and HeroVideo) to keep the code organised.

Key concepts

Image hover zoom effect

Each tile has an image that gently zooms in on hover. The trick is to set overflow: hidden on the container so the zoomed image doesn't escape its tile:

.category-tiles__img-wrap {
  overflow: hidden;   /* clips the zoomed image */
}

.category-tiles__img {
  transition: transform 0.45s ease;
}

.category-tiles__tile:hover .category-tiles__img {
  transform: scale(1.06);   /* 6% zoom */
}

The slow transition (0.45s) makes it feel smooth and intentional. The 6% zoom is subtle enough to feel premium, not gimmicky.

Label overlay with gradient

The category label sits at the bottom of each tile with a gradient behind it for readability:

.category-tiles__label {
  position: absolute;
  bottom: 0;
  left: 0;
  right: 0;
  padding: 24px 16px 14px;
  background: linear-gradient(to top, rgba(0,0,0,0.55), transparent);
  color: #fff;
  font-weight: 700;
  text-transform: uppercase;
  letter-spacing: 0.06em;
}

The gradient fades from a dark bottom (where the text sits) to transparent at the top, so the image shows through. This ensures text is always readable no matter what the image looks like underneath.

The sizes attribute on next/image

Every next/image with fill needs a sizes prop:

<Image
  src={tile.image}
  alt={tile.alt}
  fill
  sizes="(max-width: 639px) 50vw, 25vw"
/>

This tells the browser: "On screens under 640px, this image is 50% of the viewport wide (2-column grid). On larger screens, it's 25% wide (4-column grid)." The browser then picks the most appropriately sized image from the srcset, saving bandwidth on small screens.

Key concepts

lucide-react icons & the icon map pattern

lucide-react is a library of clean, consistent SVG icons. The JSON data stores the icon name as a string (e.g., "Truck"), and the component maps it to the actual icon component:

import { HelpCircle, Headphones, RefreshCcw, ShieldCheck, Truck } from 'lucide-react';
import type { LucideIcon } from 'lucide-react';

const iconMap: Record<string, LucideIcon> = {
  Truck,
  ShieldCheck,
  RefreshCcw,
  Headphones,
};

function resolveIcon(name: string): LucideIcon {
  return iconMap[name] ?? HelpCircle;   // fallback to "?" icon
}

Why not import * as icons? Importing everything from lucide-react would bundle hundreds of icons into your app. Explicit named imports mean only the four icons we use get included in the final bundle. The icon map also provides a safe fallback — if a typo appears in the JSON, HelpCircle shows instead of crashing the page.

Horizontal scroll on mobile

On mobile, four items don't fit side by side. Instead of stacking them vertically (which takes too much space), we use horizontal scrolling:

.value-props__track {
  display: flex;
  gap: 20px;
  overflow-x: auto;
  min-width: max-content;      /* prevents items from shrinking */
  -webkit-overflow-scrolling: touch;  /* smooth momentum on iOS */
}

.value-props__item {
  min-width: 200px;            /* each item stays readable */
  flex: 0 0 auto;
}

/* Hide scrollbar visually (still scrollable) */
.value-props__track::-webkit-scrollbar { display: none; }
.value-props__track { scrollbar-width: none; }

On desktop, the layout switches to flex: 1 per item and overflow: visible, so all four items spread evenly across the full width.

The sunken background

The value props strip has a slightly darker background than the page to visually separate it:

.value-props {
  background: var(--color-cream-100);  /* a shade darker than the page */
  padding: 40px 0;
}

This "sunken" effect creates visual rhythm on the page without needing borders or dividers. It's a common pattern in e-commerce sites — alternating background shades between sections.

Section 11

Split Banner

A 50/50 split of image + text content block. Used for brand messaging like "Our Promise — Made for Comfort."

Layout

Image (50%)
Text + CTA (50%)

The imageSide property in JSON controls whether the image is on the left or right:

"splitBanner": {
  "imageSide": "left",       // or "right"
  "eyebrow": "Our Promise",
  "heading": "Made for Comfort",
  "body": "Every hoodie is crafted with ...",
  "cta": { "label": "Learn More", "href": "/about", "variant": "primary" }
}

Key concepts

Conditional CSS classes

The component builds its class name dynamically based on the imageSide prop:

const className = [
  'split-banner',
  data.imageSide === 'right' ? 'split-banner--image-right' : '',
]
  .filter(Boolean)
  .join(' ');

This is the filter(Boolean) pattern. It builds an array of class names, removes any empty strings (filter(Boolean) drops falsy values like ""), then joins them with spaces. The result is either "split-banner" or "split-banner split-banner--image-right".

In CSS, the modifier reverses the layout:

.split-banner--image-right {
  flex-direction: row-reverse;    /* swap image and text sides */
}
Responsive stacking

On mobile, the 50/50 layout stacks vertically (image on top, text below):

/* Mobile: stack vertically */
.split-banner {
  display: flex;
  flex-direction: column;
}

/* Desktop: side by side */
@media (min-width: 768px) {
  .split-banner {
    flex-direction: row;
  }
  .split-banner__media,
  .split-banner__content {
    width: 50%;
  }
}

The image uses aspect-ratio: 4/3 on mobile for a natural height, and switches to min-height: 400px on desktop where it fills the height of the text content beside it.

CTA variant styling

The call-to-action button uses a dynamic class based on the variant from JSON data:

<Link
  href={data.cta.href}
  className={`split-banner__cta split-banner__cta--${data.cta.variant}`}
>
  {data.cta.label}
</Link>

This generates either split-banner__cta--primary (filled, solid colour) or split-banner__cta--secondary (outlined, transparent background). The variant comes from the JSON, so content editors can choose the button style without touching code.

Section 12

Key Patterns & Techniques

Patterns you'll see repeated across the T2 and T3 codebase.

BEM CSS naming

All T2/T3 components use BEM (Block, Element, Modifier) naming for CSS classes instead of Tailwind utility classes:

Block:    .header
Element:  .header__nav-link        (part of the header)
Modifier: .header__nav-link--active (a variant of the element)

Block:    .category-tiles
Element:  .category-tiles__grid
Element:  .category-tiles__label

Block:    .split-banner
Modifier: .split-banner--image-right
Why BEM instead of Tailwind? For complex layout components (headers, mega menus), BEM keeps the HTML cleaner and makes the CSS easier to debug. Tailwind works great for UI primitives (buttons, inputs), but a mega menu with 30+ utility classes on every element becomes hard to read. BEM and Tailwind coexist in our project — pick the right tool for the job.

Server Components vs Client Components

ComponentTypeWhy
HeroServerNo interactivity — just renders data
CategoryTilesServerStatic grid of linked images
ValuePropsServerStatic icon + text display
SplitBannerServerStatic image + text layout
AnnouncementBarClientTimer, state, dismiss handler
HeaderClientHover intent, scroll detection, menu state
MegaMenuClientFocus management, keyboard handlers
MobileNavClientDrawer state, focus trap, scroll lock

The rule of thumb: if it moves, opens, closes, or responds to user input, it's a Client Component. If it just displays data, it's a Server Component.

The barrel export pattern

An index.ts file that re-exports everything from a folder, so imports stay clean:

// types/index.ts (the barrel)
export type { CategoryTile, CategoryTilesSection, CTA, HeroSection, ... } from './home';
export type { Announcement, NavItem, MegaMenuData, ... } from './navigation';
export type { Product, Variant } from './product';

// Using the barrel — one import, many types
import type { HeroSection, NavItem, Announcement } from '@/types';
Barrel file pitfall: If any file in the barrel has a broken import or missing dependency, everything that imports from the barrel fails — even unrelated types. This happened during our T3 build. The fix: make sure every file the barrel re-exports actually exists and compiles. When debugging barrel errors, check the file the error points to, not the barrel itself.

Inline SVG icons

The components/icons/ folder holds SVG icon components. Each icon is a React component wrapping an SVG:

// components/icons/IconSearch.tsx
export function IconSearch(props: React.SVGProps<SVGSVGElement>) {
  return (
    <svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 24 24"
         fill="none" stroke="currentColor" strokeWidth="2" {...props}>
      <circle cx="11" cy="11" r="8" />
      <line x1="21" y1="21" x2="16.65" y2="16.65" />
    </svg>
  );
}

Notice stroke="currentColor" — the icon inherits its colour from the parent's text colour. This means icons automatically match the header's colour scheme (dark on light header, white on transparent header) without any extra styling.
